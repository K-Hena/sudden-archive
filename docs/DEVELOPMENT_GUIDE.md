# AI 역할 & 워크플로우 모드

이 프로젝트는 상황에 따라 두 가지 모드로 작업한다. Mode 전환은 사용자가 명시적으로 지시하며,
Claude Code가 스스로 "토큰/사용량이 부족하다"고 판단해 임의로 Mode를 바꾸지 않는다.

## Mode A — 기본 워크플로우 (기본값)

1. **Claude (Chat)** — 설계 (AI_CONTEXT상 "Technical Lead")

   - 프로젝트 구조 분석
   - 기능 설계, 아키텍처 설계
   - DB 구조 검토 / SQL 설계 (위험도에 따라 Supabase MCP로 바로 실행하거나, 고위험 SQL은 사용자 확인 후 실행 — 아래 "SQL 실행 규칙" 참고)
   - 코드 리뷰, 버그 원인 분석
   - Claude Code 작업 지시서 작성
   - 구현 방향 결정
   - 디자인 시안 제시 (버튼 스타일, 아이콘 등 — 확정 전에는 시안으로만 제시하고, 사용자가 "이대로 만들어줘"라고 확정하면 실제 파일 생성)

   구현 전에 항상 Claude와 설계를 먼저 진행한다.

2. **Claude Code** — 구현 (AI_CONTEXT상 "Developer")

   - 실제 코드 구현
   - 여러 파일 수정
   - 리팩터링
   - Git 작업 (커밋, 푸시 포함)

   설계 변경은 Claude(Chat)와 협의 후 진행한다. 담당 업무의 자세한 행동 규칙은 아래 "Claude Code 행동 원칙" 이하 섹션 참고.

3. **Codex** — 리뷰어
   - 설계 단계가 아니라 **Claude Code가 코드를 수정한 직후, 턴이 끝나기 전에** 자동으로 검토한다 (`stop-review-gate`, 플러그인 내장 기능)
   - git diff(실제 변경된 코드)를 기준으로 검토하며, 별도 명령이나 창 없이 Claude Code 안에서 자동 실행된다
   - 문제가 발견되면 턴을 멈추고 사용자에게 보고한다
   - 사용자가 `/codex:setup --enable-review-gate`를 한 번 실행해둬야 동작한다 (Claude Code가 대신 실행하지 않음)
   - **VS Code 확장/사이드바 세션에서는 자동 발동이 관찰되지 않는 경우가 있었다** (설정 자체는 `/codex:setup`으로 정상 확인됨 — 실행 환경 문제로 추정, 터미널 통합 세션에서는 정상 동작할 가능성이 있으나 아직 확정 검증되지 않음). 코드 수정 후 자동 리뷰가 뜨지 않으면 아래 "커밋 전 필수 리뷰 규칙"에 따라 `codex:rescue`로 수동 요청한다. 향후 터미널 세션에서 자동 발동이 확인되면 이 문구를 갱신할 것

## Mode B — 대체 워크플로우 (Claude Code 사용량/토큰 소진 시)

1. **GPT (ChatGPT)** — 설계 (Claude Chat 대체)
   - Mode A의 Claude(Chat) 담당 업무를 동일하게 수행한다
   - 사용자가 ChatGPT와 별도로 설계를 진행하고, 그 결과(지시서)를 Codex에게 전달한다

2. **Codex** — 구현 + 리뷰 (Claude Code 대체)
   - GPT가 작성한 지시서를 바탕으로 코드를 직접 구현한다 (Codex CLI, 또는 Claude Code 안에서는 `codex-rescue` 서브에이전트로 위임 가능)
   - 구현 후에는 Mode A와 동일하게 `stop-review-gate`가 자동으로 리뷰한다
   - Git 작업(커밋/푸시)도 이 문서의 동일한 규칙을 따른다

# 코드 스타일 규칙

## 기본 원칙

- 기존 코드 스타일 유지
- 필요한 파일만 수정
- 새 파일 최소 생성
- 기존 기능 유지
- 추측 금지

## JavaScript

- Vanilla JavaScript 사용
- 함수는 하나의 역할만 수행
- 의미 있는 이름 사용
- 중복 코드 최소화

## HTML

- 기존 구조 유지
- 불필요한 태그 추가 금지

## CSS

- 기존 디자인 유지
- 공통 스타일 재사용

## 파일 수정 / 구조 변경

가능

- 버그 수정
- 기능 추가
- 기존 코드 개선

사용자 승인 필요 (하지 말 것)

- 새 폴더 생성
- 새 라이브러리 추가
- 프로젝트 구조 변경 / 재설계
- 기술 스택 변경
- 파일 대량 생성
- 대규모 리팩터링

## 주석

코드를 설명하지 않는다.

왜 필요한지를 설명한다.

## 에러 처리

Supabase 호출(`sb.from(...)`, `sb.auth...`, `sb.storage...`)은
반환되는 `{ data, error }`의 `error` 필드로 확인한다. (Supabase 클라이언트는 실패 시 예외를 던지지 않고 error를 반환한다)

라이브러리 초기화 등 예외가 실제로 발생할 수 있는 코드만 try-catch로 감싼다.

없는 곳에 불필요한 try-catch를 추가하지 않는다.

## Git

하나의 기능 = 하나의 Commit

의미 없는 Commit 금지

# Claude Code 행동 원칙

당신은 설계자가 아니다. 당신은 구현 담당 개발자이다. 프로젝트 설계는 `docs/AI_CONTEXT.md`를 따른다.

## 반드시 할 일

- 프로젝트 전체 구조를 먼저 이해한 후 작업한다
- 기존 프로젝트/코드를 존중하고, 기존 기능을 임의로 변경하지 않는다
- 필요한 파일만 수정하고 영향 범위를 확인한다
- 과도한 리팩터링을 하지 않는다
- DB 구조는 임의로 변경하지 않는다 (아래 "SQL 실행 규칙" 참고)
- 구현 → 코드 리뷰 → Git Push 순서를 지킨다

## 모르면

절대 추측하지 않는다. 질문한다.

## 구현 철학

최소 수정 → 최대 안정성 → 기존 코드 존중

## 코드 작성

간결하게, 읽기 쉽게, 기존 스타일을 유지해서 작성한다.

## 최종 목표

사용자의 프로젝트를 더 좋은 프로젝트가 아니라, 더 안정적인 프로젝트로 만든다.

## 말투 규칙

- 코드 주석, 커밋 메시지, 작업 중 스스로 판단을 남기는 혼잣말(예: "일단 이 함수부터 확인해보자" 같은 사고 과정)은 편한 톤으로 써도 된다.
- 하지만 사용자에게 직접 말을 거는 모든 응답 — 작업 결과 보고, 질문, 확인 요청, 에러 설명 등 — 은 항상 존댓말(정중한 톤)로 작성한다.
- 판단 기준: "이건 사용자가 읽으라고 쓰는 문장인가?"라고 자문해서, 그렇다면 존댓말을 쓴다.

# SQL 실행 규칙 (2026-07-20 변경)

기존 "SQL은 작성만 하고 사용자가 직접 실행한다"는 규칙을 위험도 기준으로 세분화한다.

## 자동 실행 가능 (Supabase MCP 플러그인 사용)
- SELECT (조회)
- INSERT (데이터 추가)
- UPDATE (데이터 수정)

## 반드시 사용자 확인 후 실행
- DELETE (데이터 삭제)
- DROP / TRUNCATE (테이블·데이터 전체 삭제)
- CREATE TABLE (테이블 생성)
- ALTER TABLE (구조 변경, 컬럼 삭제 포함)
- RLS 정책 생성/변경/삭제

이 경우 실행 전 반드시 다음을 사용자에게 명시한다:
- 무엇을 실행하려는지
- 되돌릴 수 없는 작업임을 명확히 고지
- "진행할까요?" 확인을 받은 후에만 실행

## 이유
사용자가 비전공자로 SQL 자체의 위험도를 스스로 판단하기 어렵기 때문에,
이 구분과 판단은 항상 Claude Code/Claude Chat이 대신 수행한다.

# 커밋 전 필수 리뷰 규칙 (Mode A 기본)

이 프로젝트의 기본 협업 흐름은 Mode A(Claude Chat 설계 → Claude Code 구현 → Codex 리뷰(자동 발동 시 자동, 미발동 시 codex:rescue로 수동) → 커밋)이다.
지시서(프롬프트)에 "Codex 리뷰"에 대한 언급이 없더라도, 아래 절차를 항상 스스로 따른다 — 지시서에 없다는 이유로 리뷰를 건너뛰지 않는다.

1. 코드 변경을 완료한다 (아직 커밋하지 않는다).
2. 변경된 diff를 Codex에게 리뷰 요청한다.
3. Codex의 리뷰 결과(승인/지적 사항)를 받는다.
   - 지적 사항이 있으면 반영 후 다시 diff를 정리한다.
   - 승인되면 다음 단계로 진행한다.
4. 그 다음에만 git add / commit / push를 진행한다.

예외: 사용자가 명시적으로 "이번엔 리뷰 없이 바로 커밋해줘"라고 말한 경우에만 이 절차를 건너뛴다.
Claude Code 토큰이 부족해 Mode B(GPT 설계 → Codex 리뷰+구현+커밋)로 전환된 경우, 이 규칙은 GPT/Codex 쪽 워크플로우에 준하는 절차로 대체된다 (Claude Code가 직접 수행하는 경우가 아니므로).

이 예외는 사용자의 명시적 요청이 있을 때만 적용되며, 다음과 같은 경우에도 예외로 인정되지 않고 동일하게 리뷰를 거쳐야 한다:
- Mode A/B 전환이 진행 중인 경우
- 변경이 사소해 보이는 경우
- 이미 이전에 리뷰받은 코드를 그대로 재사용하는 경우

만약 실수로 리뷰 전에 커밋·push했다면, 그 시점에 바로 사후 리뷰를 받고 그 사실과 원인을 작업 보고서에 명시한다.

작업 보고 마지막에 항상 아래 항목을 포함한다:
"이번 작업에서 Codex 리뷰를 거쳤는지 여부, 거쳤다면 리뷰에서 나온 지적 사항이 있었는지" — 사전 리뷰가 아니라 사후 리뷰였다면 그 사실과 원인도 함께 적는다.

## 예외: 순수 문서(.md) 전용 커밋

코드(`app.js` 등) 변경이 전혀 없고 `.md` 파일만 수정한 커밋은 위 Codex 리뷰 절차를 생략할 수 있다.
변경 사항 중 코드가 하나라도 포함되면(문서와 코드가 같은 커밋에 섞여 있어도) 예외 없이 기존 규칙대로 리뷰가 필수다.

# 지시서 범위 밖 변경을 발견했을 때의 되돌림 기준

작업 중 지시서 범위 밖의 변경(코드/문서 무관)을 발견하면 다음 기준으로 판단한다.

- 판단 기준은 **"커밋됐는가"**이지 "푸시됐는가"가 아니다. 커밋은 이미 누군가 의도적으로 확정한 작업이라는 뜻이므로, 아직 푸시 전이라도 함부로 되돌리지 않는다.
- 그 변경이 **아직 커밋되지 않은 상태(uncommitted)**라면, 이번 작업과 무관하다고 판단 시 되돌려도 된다. 단, 되돌리기 전 발견 사실과 이유를 작업 보고서에 반드시 남긴다.
- 그 변경이 **이미 커밋된 상태**라면(푸시 여부 무관), 이번 작업과 무관해 보여도 **절대 되돌리거나 수정하지 않는다.** 다른 세션에서 사용자가 승인한 정당한 작업일 가능성이 높다.
- 커밋 여부가 애매하면 `git log`로 먼저 확인하고, 확인 없이 임의로 되돌리지 않는다.
- 이미 커밋된 범위 밖 변경이 정말 문제가 있어 보인다면(예: 명백한 실수), 되돌리지 말고 **사용자에게 알리고 판단을 구한다.**
- **커밋됐지만 푸시가 안 된 상태를 발견했다면**, 그 자체를 "이상한 상태"로 보지 말고, 단순히 아직 푸시 단계까지 못 간 정상적인 작업 흐름일 수 있음을 감안한다. 필요하다면 되돌리는 대신 **그대로 푸시를 마저 진행하거나, 사용자에게 푸시해도 되는지 확인**하는 쪽을 우선 고려한다.

## 범위 밖 미추적 파일/폴더 처리

지시서 범위 밖에서 발견된 미추적(untracked) 파일/폴더는, Codex 리뷰 등에서 실제로 문제로 지적되지 않는 한 별도 조치 없이 그대로 둬도 된다. `KNOWN_ISSUES.md` 기록도 필수는 아니다 (위 되돌림 기준은 이미 존재하는 변경을 대상으로 하며, 애초에 이번 작업과 무관한 미추적 파일까지 매번 조사·기록할 필요는 없다는 뜻이다).

# 작업 완료 보고 체크리스트 규칙

지시서에 "테스트 확인 사항" 목록이 있으면, 완료 보고 시 이 목록을 서술형으로 요약하지 않고 항목을 그대로 가져와 하나씩 표기한다.

- ✅ 확인함
- ❌ 누락되었거나 확인하지 못함
- ➖ 이번 작업과 무관해 해당 없음

❌로 표기한 항목이 있으면 왜 확인하지 못했는지 이유를 함께 적는다. 이유 없이 빠뜨리지 않는다.

예시(진영 선택 로직 지시서 기준):
- ✅ mTeam select 옵션이 RED/BLUE + "선택 안 함(공통)"만 있는지
- ✅ 추가 모달이 항상 미선택으로 시작하는지
- ❌ 미선택 저장 항목을 즐겨찾기 추가 시 FAVORITE에도 표시되는지 — 최초 보고에서 누락, 사용자 지적 후 추가로 확인함

# 문서 유지보수 규칙

새로운 기능을 구현하거나 기존 기능을 변경한 경우, AI는 반드시 아래 규칙을 확인하여 필요한 문서를 함께 수정해야 한다.
모든 문서는 각자의 책임을 가지며, 하나의 변경 사항이 여러 문서에 영향을 줄 수 있다. 문서를 최신 상태로 유지하는 것은 코드 작성만큼 중요하다.

전체 문서 목록과 각 문서의 역할은 `docs/AI_CONTEXT.md`의 "문서 지도" 표를 참고한다 (이 문서에서 별도로 반복하지 않는다).

## 변경 유형별 확인

### 새 기능 추가

확인
- AI_CONTEXT의 "진행 중인 기능 개발" 섹션 — 완료된 작업 체크, 남은 작업 갱신

필요시
- AI_CONTEXT의 확정된 설계 결정 섹션

### 기존 기능 수정

확인
- 특별히 없음 (커밋 메시지로 변경 이력을 남기는 것으로 충분)

필요시
- 진행 중인 작업의 일부라면 AI_CONTEXT 진행 상황 갱신

### 버그 수정

확인
- 특별히 없음 (커밋 메시지에 원인을 남긴다)

필요시
- 같은 문제가 반복될 가능성이 있다면 AI_CONTEXT에 참고 기록 추가

### DB(Supabase) 변경

반드시
- SQL은 Claude Chat과 먼저 설계한다. 실행은 위험도에 따라 다르다: SELECT/INSERT/UPDATE는 Supabase MCP로 Claude Code가 바로 실행 가능, DELETE/DROP/ALTER TABLE/RLS 정책 변경은 사용자에게 명시하고 확인받은 후에만 실행 (위 "SQL 실행 규칙" 참고)
- AI_CONTEXT의 관련 섹션(시스템 구조 / 설계 결정) 갱신

### 프로젝트 구조 변경 (서비스 구성, 시스템 구조)

반드시
- AI_CONTEXT의 서비스 구성 / 시스템 구조 섹션

### 설계 변경

반드시
- AI_CONTEXT의 확정된 설계 결정 섹션

### Master / 관리자 기능 작업

확인
- AI_CONTEXT의 "진행 중인 기능 개발" 섹션에서 완료된 작업에 체크, 남은 작업 갱신
- sudden-archive-admin의 로직을 이식한 경우, 이식 범위(이번 단계에 포함/제외한 것)를 남은 작업에 명확히 남긴다

### AI 작업 방식 변경

확인
- DEVELOPMENT_GUIDE.md (이 문서)
- PROMPTS.md

## 문서 수정 원칙

- 불필요한 수정은 하지 않는다.
- 책임이 다른 문서의 내용을 복사하지 않는다.
- 중복이 필요한 경우에는 유지한다.
- AI_CONTEXT는 프로젝트의 기준 문서로 유지한다.
- 변경 사항이 발생하면 관련 문서를 함께 검토한다.

## 문서 자동 동기화 규칙 (모든 작업 종료 시 필수 실행)

사용자가 "AI_CONTEXT.md만 읽고 진행해줘"처럼 특정 문서만 언급했더라도,
작업 종료 직전 아래 체크리스트를 항상 스스로 점검한다.
사용자에게 "어떤 문서를 고쳐야 할지" 판단을 요구하지 않는다 — 그 판단은 항상 이쪽에서 한다.

- 새 기능을 추가/구현했다 → TODO.md에서 해당 항목을 완료로 옮기고, CHANGELOG.md에 한 줄 추가
- 버그를 수정했다 → TROUBLESHOOTING.md에 원인/해결 기록 (재발 방지 가치가 있는 경우만)
- 설계/방식을 새로 결정했다(예: 라이브러리 선택, 구조 변경) → DECISIONS.md에 결정과 이유 기록
- DB 스키마/RLS 관련 SQL을 새로 제시했다 → DATABASE.md 갱신 필요 여부 확인
- 인증/검색/관리자/DB 흐름 관련 코드를 바꿨다 → `ARCHITECTURE.md`의 해당 섹션(인증/탐색·검색/관리자/데이터베이스 흐름) 갱신 필요 여부 확인
- 폴더/파일 구조가 바뀌었다 → `ARCHITECTURE.md`의 "폴더/파일 구조", "index.html 내부 구성" 갱신 필요 여부 확인
- 위 어디에도 해당 안 되는 단순 작업(질문 답변, 사소한 수정 등)이었다 → 문서를 건드리지 않고, 보고서에 "해당 없음"이라고 명시
- 작업 중 지시서 범위 밖의 이슈를 발견했지만 이번 작업에서 고치지 않기로 판단했다 → `KNOWN_ISSUES.md`에 기록(추측이나 단순 개선 아이디어가 아니라 실제로 확인된 이슈만)
- `KNOWN_ISSUES.md`에 있던 이슈를 실제로 고쳤다 → 해당 항목을 제거하고 `CHANGELOG.md`에 기록. 재발 방지 가치가 있으면 `TROUBLESHOOTING.md`에도 원인·해결·예방 기록

작업 보고 마지막에 항상 아래 항목을 포함한다:
"이번 작업으로 자동 갱신한 문서: (목록 또는 없음)"
